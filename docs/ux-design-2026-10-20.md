# amt-console: UX and visual design

Design note, 2026-10-20, revision 2 (after the adversarial review `docs/ux-review-2026-10-20.md`). Status:
proposed, not granted. Design only: no app code, nothing deployed. The operator's words that are the
requirements:

1. "before we retire meshcommander, we need an end to end managemenu ui of our own. it should follow our
   ux guidelines / requirements and use the amt mcp for all amt actions"
2. "a ux graphics designer to design a full proffessional ui with untuitive control and management
   services that surpassess that of other collaboration / meeting tools embodying the material framework,
   offer dark and light themes, and elaborates beyond it when its expressive need is beyond that of the
   capabilities provided?" For this product the comparison set is remote-management consoles:
   MeshCommander, MeshCentral, Intel EMA, Dell iDRAC, HPE iLO, Proxmox.
3. Server entries must be managed, not hard-coded, "in the same interface or similar interface for where
   you're managing the identity information" (identities = the credentials each server uses).
4. (2026-10-20 12:54 EDT) Every action the UI performs, AMT or management, goes through an amt-mcp MCP
   tool, built where missing; no MCP tool may carry a secret value in its arguments or results; ISO image
   management (list, fetch with checksum, upload, verify, rename, delete) belongs in the console.

Operator decisions since the review (binding on this revision):

1. **Every UI action uses an amt-mcp tool.** The console never writes the vault, the devices file or the
   image root itself; it calls tools. The console backend holds no write path into amt-mcp's state.
2. **One real server.** Only my-server-1 supports AMT today; the invented servers are gone. The design
   still scales to many (section 2.2).
3. **Live keyboard and mouse** in the mirror and serial embeds use the pages' control-token input route,
   not a tool: the ONE named exception to decision 1 (census rows 18 and 24 of the review). **Record is
   not an exception** (operator ruling, 2026-10-21, sprint review M1): it is `record_start` (with
   `confirmed: true`, behind a plain sheet) and `record_stop` of `amt_mirror_link` / `amt_serial_link`, offered
   from the console's own session card; the framed page has no Record control and its `record` route is
   refused in embed mode.
4. The mirror page's own Power, Boot and ISO rows **stay on the standalone page**, routed by the server
   through the real tools with the console's confirm standard. Whether the console's **embed** shows them is
   the designer's call: **it does not** (section 2.5, the embed decision).
5. ISO image management is part of the console: list, verify, fetch with sha256, upload (one-time PUT url,
   exact size, optional sha256), rename, delete; busy refusals (mounted, downloading, uploading).
6. Credentials: variant A (the console takes a password into the NAS vault) is kept, but only through a
   **one-time intake url minted by an MCP tool**; no secret in any tool argument or result; identities are
   write-only, status by name.

No screen ever displays a secret value: entry fields only, never a reveal, status shown as present / where
used / updated-at.

## 1. Design principles

1. **The host's truth, not the console's guess.** Every state on screen comes from a tool result and says
   when it was read ("read 8 s ago"). Power state, offered actions, the next-boot flags, who holds the
   KVM session, what a read could not cover (`unavailable`, `truncated`, `undated`): shown as the tool
   returned them, never inferred from the last click.
2. **Every write is a deliberate act with its consequence in plain words.** A write button opens a sheet
   that says what will happen to the host in the tool's own vocabulary (graceful or not, data lost or not,
   session held or released), names the exact `tools/call` with `confirmed: true`, and only then sends.
   Whether the act is destructive is decided from the **arguments** the call would carry, never from which
   button opened the sheet; a destructive act takes a second, physically different step: hold to confirm
   (section 5).
3. **One session per host, and the holder has a name.** AMT allows one KVM session; the console shows
   who holds it (you, an agent through the mirror, another client), since when, and what that means for
   the next action (opens refused). An agent's work is watched, not fought: while the mirror runs, the
   agent's screenshots and typing share it, the console shows when an agent's call is typing and pauses
   the operator's input for that moment, and stopping an agent's session is a destructive step.
4. **Refusal is a first-class result.** A tool's refusal ("AMT offers only hard_reset and nmi right now",
   "screen_not_expected:saw=linux-console", "presents leaf X, not the given pin") is rendered verbatim,
   with "nothing sent", where the action was. There is no retry loop: one logon attempt, one Digest
   attempt, one pin check, and the console says so; a refused credential pauses polling of that server.
5. **Secrets have names, never values, and never ride a tool.** Identities are managed by name, kind,
   owner server, where used and status (present, updated-at). A value is typed once into a one-time url
   that amt-mcp minted, and amt-mcp writes it into the NAS vault in-process. Fingerprints are shown in full,
   because they are not secrets; passwords, viewer tokens and bearers never appear in a page, a URL, a log
   line, a tool argument or a tool result. The console's own bearer is console-specific (S1), so a console
   compromise is a console compromise, not a fleet one.
6. **Servers and identities are one management area, and amt-mcp owns both.** Adding a server names its
   identities on the same form (requirement 3); a new identity is minted in Identities first; removing a
   server never silently deletes them. The console calls `amt_device_manage` and `amt_identity_manage`; it
   holds no file of its own.
7. **Material 3 by default, extended where a host console needs it.** Every surface, type role, shape and
   motion value is M3. Where M3 has no vocabulary (a held session, a verified pin, a refused call, a
   destructive hold, a fingerprint) the extension is a named token in `tokens.json`, justified in section
   7, with the same contrast floor as the M3 roles.
8. **Phone is a layout, not a lesser client.** Every control exists and is reachable at 360 px: a bottom
   navigation bar, a scrolling section row that shows the current section, card-per-row tables, bottom
   sheets for every confirmation, 1-up cards, no fixed element over a control.

### Where this beats MeshCommander, MeshCentral, Intel EMA, iDRAC, iLO and Proxmox

## 2. Information architecture

One operator client (passkey sign-in). Navigation has four top-level sections in a navigation rail
(phone: a bottom navigation bar): **Fleet** (all servers; a server opens its own page), **Manage** (servers
and identities, one area with two tabs), **Images** (the IDE-R image library and the mounts), **Settings**
(console preferences and passkeys; the per-server AMT settings live on the server page). A server page
carries a persistent header (name, power pill, address and AMT version, session chips, pin chip) and nine
sections as tabs (phone: a scrolling chip row): Status, Power & boot, Console, Serial, Media, Logs,
Inventory, AMT settings, Advanced.

Every screen below is listed with purpose, regions, every control mapped to its MCP tool, states, and the
parity rows it serves (section 8 numbers). Every action is a `tools/call` from the console backend to
amt-mcp's `/mcp` with the console's own bearer; the browser never calls amt-mcp's MCP endpoint. Two things
reach amt-mcp from the browser directly and are not tools, both by design: live keyboard and mouse in the
embedded viewer pages (their control-token `input` route, decision 3), and the one-time PUT of a file
(image upload) or an identity value (intake) to a url a tool minted, which is single-use, outside the
bearer gate and never carries the value through MCP.

### Tool surface this design is cut against

Built at HEAD (20 tools, live schema): `amt_status`, `amt_screenshot`, `amt_inventory`, `amt_logs`,
`amt_settings`, `amt_wsman_get`, `amt_devices` (list / show / pin_check), `amt_remote_logon`,
`amt_remote_logoff`, `amt_power`, `amt_set_next_boot`, `amt_console_input`, `amt_sol`, `amt_ider`,
`amt_images` (list / verify / set_root / fetch / upload / rename / delete), `amt_configure`,
`amt_wsman_invoke`, `amt_mirror_link`, `amt_serial_link`, `amt_device_manage` (add / edit / remove, `repin`,
`expected_pin`, refuses the last server and a changed leaf without `repin`). Planned, designed against by
name (argument names below are proposals the server engineer may rename; the mockups' call lines change
with them): `amt_identities` (read: per entry name, kind, owner, used-by, present, updated-at; never a
value), `amt_identity_manage` (write, confirmed: `intake` mints a one-time PUT url, `remove` refused while in
use), `amt_captures` (read: past screenshots, MP4s and casts with a fresh one-time url per item). Not tools
and designed as unavailable: Platform Erase, the AMT admin-password change.

### 2.1 Sign in, enrollment, session expired (`sign-in.html`)

- **Purpose.** Passkey (WebAuthn) sign-in to the console; no password exists. The first passkey is
  enrolled with a one-time code the operator mints from the admin command set; later passkeys are added
  from a signed-in session (Settings).
- **States (five, one card each).** *Sign in*: "Sign in with passkey" (filled), the LAN-only note, a
  link to enrollment. *Waiting*: indeterminate progress while the authenticator is up, Cancel. *Enroll*:
  the command `amt_admin.py console enroll-code` (S1), a 3-group one-time code field (12 characters,
  10-minute single-use validity), a passkey name, "Create passkey". *Expired*: "signed out after 12 hours
  idle", with the live-colored banner "nothing on the hosts changed: a KVM mirror or serial terminal you
  started is still held by amt-mcp". *Refused*: the passkey is not enrolled; nothing was sent to any host;
  the console logs the passkey id only.
- **Security model (review M14).** Session cookie `Secure; HttpOnly; SameSite=Strict`; every
  state-changing route requires a same-origin `Sec-Fetch-Site` / `Origin` check and a per-session CSRF
  token; the console sends `Content-Security-Policy: default-src 'self'; frame-src 'self';
  frame-ancestors 'none'` (the viewer pages are relayed under the console's own `/embed/` path, so no other origin is framed) and `Referrer-Policy: no-referrer`; the viewer pages send `frame-ancestors
  <console origin>` (S1). The relayed viewer pages are served on the console's own origin, so the frame that
  holds one is **opaque** (sprint review B1, operator ruling 2026-10-21): the iframe carries
  `sandbox="allow-scripts allow-forms"` (no `allow-same-origin`) and `referrerpolicy="no-referrer"`, and the
  relayed response carries the same CSP `sandbox allow-scripts allow-forms`, so a copy opened in a tab is
  opaque too. The relayed script cannot reach the console page's DOM, globals or cookie, nor call `/api`
  (the embed CSP `connect-src` is the absolute `<origin>/embed/`; an opaque document has no `'self'`). The
  cookie (`SameSite=Strict`) cannot ride an opaque frame, so every route under `/embed/` is authenticated by
  a **per-page-view embed key** in the path, `/embed/<kind>/<server>/<key>/`: `secrets.token_urlsafe(32)`,
  minted by the session-authed `POST /api/embed/key {kind, device}` (cookie, CSRF token and a known server),
  kept in memory only (a digest, never the key), bound to the minting session and to that one (kind, server),
  compared in constant time against every kept digest, and dead at sign-out, when its session expires, after
  **10 minutes unused** (any request with the key, or the open page's own state poll, restarts the clock;
  the poll's reply says `key_live` so the page mounts a fresh frame when the key is gone, e.g. after a console
  restart), or when the process restarts; at most 256 live. A stream already open under the key (MJPEG `stream`, serial `events`)
  is re-checked every 2 s, quiet or busy, and ends the first time the key is dead (so sign-out and session expiry cut it too; an open
  stream counts as a use of the key). A wrong, expired, revoked or other-server key
  is a 404 with nothing sent upstream. The key-authed `/embed/` paths answer CORS for the opaque frame's
  `Origin: null` (`Access-Control-Allow-Origin: *`, never credentials, a preflight for the JSON `input` POST);
  a POST there needs `Origin` `null` or the console's own; every other route keeps the exact-Origin, cookie
  and CSRF rules. The key is in no log line (`loggable()` masks it), no `Referer` (`no-referrer`), no error
  body, no upstream request and no file; the frame's own `src` and "Open in a tab" are the only places it is
  written down. The hold is a safety mechanism, not a clickjacking defence; the framing headers are.
- **Tools.** None: the console backend's own auth. Nothing here reaches amt-mcp.

## 3. Flows

Each flow names its screens, the calls in order, and the states the operator sees.

**Add a server end to end.** Manage → Identities → New identity: name `<key>-amt`, kind AMT admin password,
owner → Mint the intake (`amt_identity_manage intake`) → type the password once, Send (the browser's PUT to
the one-time url) → "received · present". Manage → Servers → Add server: key, address, ports, the identity
names, optional expected pin → Add server (confirm sheet: `amt_device_manage add` reads and pins the leaf
or refuses against the expected pin, writes devices.json, then `amt_status {device}`) → the result row:
pin recorded (full fingerprint, compare with MEBx), status succeeded / failed with the reason (a wrong
password shows as `wsman_auth_failed_401` after one attempt, never retried, and the fleet card goes to
paused) → the server appears in the fleet with its pin chip "matches".

**Power and boot.** Server → Power & boot: the offered set is read first; a graceful action opens its
confirm sheet (consequence, the exact call) → Confirm → "Sending…" → accepted with ReturnValue and the
readback (or readback unavailable), or refused verbatim, nothing sent. A forced action: open the Force
tray → the action's sheet (error-colored consequence, "the OS is NOT asked") → hold 1.2 s and release
(or press, then confirm on the second sheet, which arms 400 ms after the release that follows its
opening) → sent. Boot into BIOS: choose the target → Reset → target (the hold) → `amt_set_next_boot` then
`amt_power hard_reset`, the second not sent if the first is refused → the "AMT reports" chip shows the
override until the host restarts; the console view shows the BIOS. Tick `secure_erase` and press Set next
boot only → the sheet is the hold, because the request is.

**Console takeover.** Server → Console: if no mirror runs, "Start mirror" (confirm: the exact call with
`bind 0.0.0.0`; opens the host's single KVM session; viewers get a view token, you the control page framed
through the console route; agents will share it) → the embed loads in embed mode → Take control in the
embed → the controlling strip; leaving the window releases → key macros or a text step with a screen
guard, or the host sign-in (one attempt; an abort is shown with its reason and no retry control) → while
an agent's call types, the strip says so and your input is paused → Stop mirror releases the session (a
plain confirm for your own idle mirror; the hold when an agent started it or a call is in flight). If
another client holds the session the start is refused with "another session is open" and the console says
it cannot take it over.

**Serial.** Server → Serial: Start terminal (confirm, exact call) → the xterm embed shows the scrollback
then the live stream → Take control in the embed, or Send a line (confirm; shared with the terminal) →
Sign in on serial (one attempt) → Start / stop recording → the .cast appears as a capture result (listed
by `amt_captures`, fetched once, sha256 verified, Save) → Stop terminal.

**Media mount.** Images (or Server → Media): pick an ISO from the library (fetch one by URL with an
expected sha256, or upload one: the tool mints a one-time PUT url for the exact size, the browser sends
the file, the table shows progress and the size/hash check at the end) → Mount with `next_boot` (confirm;
the host is not reset) → the header's IDE-R chip goes live → boot from it: Power & boot, target `cd_ider`,
Reset → (the hold) → Unmount when done (confirm; "session still held" if the serving thread will not
stop). Verify, Rename and Delete (the hold) on a free image; refused with the reason while it is mounted,
downloading or uploading.

**Logs and events.** Server → Logs: choose event or audit, a window, read → rows with severity and raw
data; the footer counts; paging; an empty page is explained against the fetched count.

**Inventory.** Server → Inventory: sections, cards, the coverage banner; Export JSON.

**Settings.** Server → AMT settings: pick an area → change writable fields → the old/new preview →
Write (confirm) → written and read back, `previous` kept, Revert available; a credential-named field is
refused before anything is sent.

**Identities.** Manage → Identities: New identity → Mint the intake → Send the value → present; Replace
stored value (after changing the password in MEBx) → Remove (refused while used; the hold otherwise).

**Sign-in.** Passkey → waiting → the fleet. First time: mint the one-time code in a terminal → Enroll →
Create passkey → the fleet. Later passkeys: Settings → Add a passkey. Expired: sign in again; sessions on
the hosts survived.

## 5. Interaction design for control and management

### 5.1 The write confirmation (every write)

A write control opens a bottom sheet (desktop: the same sheet, centered, 640 px) with: a title that names
the action and the server ("Restart my-server-1 (graceful)"), the **consequence line** in the extended
`consequence` type role (16/24/500) on `surface_container_highest`, the exact `tools/call` in `data`
type with `confirmed: true` and the explicit `device`, Cancel (text button) and Confirm (filled). The
sheet is `role=dialog aria-modal`; opening it by key or by pointer moves focus to Cancel, Tab stays inside
it, and closing it returns focus to the control that opened it (review M5). One deliberate activation
sends one call; `event.repeat` is ignored so a held Enter sends one, not many (measured on every confirm
sheet, section 11). The sheet closes on confirm; the result lands in the action's card as a `.result` row
with the time.

**The kind of sheet follows the arguments (review B3).** A control that can send a destructive request or
a harmless one depending on what the form holds (Set next boot with or without a destructive option; a
mount with `next_boot` or `now`; stopping a session the console owns or an agent's) computes its call at
open time and opens the plain sheet or the destructive one from one predicate over that call's arguments;
the consequence line is rendered from the same predicate, and the mocked call carries the real `options` or
`start`. The build keeps one such predicate in the client, and its request spy asserts that every sent call
satisfying it was preceded by a force fire.

### 5.2 The destructive second step (the force control)

The destructive set, by argument: every ungraceful power action (hard_reset, hard_power_off,
hard_power_cycle, immediate_shutdown, immediate_power_cycle, nmi), Reset → target (it is a hard reset), a
next-boot request carrying `secure_erase`, `reflash_bios` or `configuration_data_reset`, an IDE-R mount
with `start: "now"` (`graceful` is the same act as Restart, a plain confirm), deleting an image, removing a
server or accepting a changed leaf (`repin: true`), removing an identity, Unprovision, and stopping a mirror
or terminal an agent started or that has a call in flight. The sheet's consequence line is on
`error_container` (white text) with the warning glyph, and in place of Confirm it carries the **force
control**: the only labelled pill among the action controls, `error` fill, "Hold to <verb>". Pointer: a
hold of 1200 ms; from the first millisecond the whole control is `hold.fill` with the label in
`on_error_container` and a thin `on_error_container` bar grows under the label (review M23: no part of the
label ever sits on `error`); the **release** fires (up-event completion, SC 2.5.2); releasing early,
leaving the control or swiping cancels; the click that follows a fired hold is swallowed. A short press, a
tap, a key press or an assistive-technology activation opens a **second sheet** whose "<Verb> now" button
**arms only 400 ms after a release (keyup or pointerup) that happened after the sheet opened** — never on a
timer from the opening activation — and a pointer click fires only if its own pointerdown landed while
armed (review B1): two slow taps at one spot never fire, because the second tap's release is what starts
the 400 ms and its click arrives before they pass; the third deliberate tap, on a button that is visibly
armed, fires. The second sheet lays its action row **above** the consequence, so the confirm is never under
the point where the opener was, and focus goes to Cancel; `event.repeat` is ignored on both. Under reduced
motion the bar is replaced by a 3-2-1 countdown on the same `hold.fill` and the 1200 ms is kept (a safety
delay, not decoration). This is the house kill-switch mechanism (agent-meetings, immutable 8 there),
renamed and placed inside the confirmation sheet; its matrix was run on all 16 force controls in the
mockups at 1024 and 360, pointer, touch and keyboard (section 11).

### 5.3 Sessions

The holder is on the server header, on the console and serial pages and in the sessions panel, from
`amt_mirror_link status` / `amt_serial_link status` / `amt_ider status`. "You" means the console started
it and holds the control token; "agent via mirror" means an agent started it; "another client" means
amt-mcp could not open the session and the console cannot take it over. The console starts every mirror and
terminal itself with `bind: "0.0.0.0"` and `port: 8766` behind the viewer front, so an agent's session on
the same server is framed the same way; an agent's mirror started with the tool default `127.0.0.1` is
reported as not reachable from here. While an agent's call holds the session (the mirror's `status.json`
in-flight state), the console shows the agent-typing strip and releases the operator's control for that
window. Stop mirror / Stop terminal is a plain confirm for the console's own idle session (it releases a
session, never the host) and the hold when an agent started the session or a call is in flight, because
then it ends a sequence under the agent (review M15).

### 5.4 Screenshots, recordings and captures

The backend fetches the one-time `url` once, immediately, verifies the `sha256` from the tool result,
and stores the file in the capture store (per operator session, retention 24 h); the page shows the
capture card with the hash grouped by 4 and "verified", Save (a download from the console's own
authenticated route), Copy sha256. A capture whose link expired (the backend could not fetch within 15
minutes, e.g. the console was down) is shown as expired, never as missing. Recordings go to the NAS folder
amt-mcp reports (`recording_dir`); finished MP4s and casts, and past screenshots, are listed by
`amt_captures` with a fresh one-time url per item and pulled into the store the same way. The embed's own
download buttons are not shown (embed mode), so every capture goes through this one path.

### 5.5 Keyboard shortcuts

`g f` fleet, `g m` manage, `g c` console (current server), `g p` power, `/` filter, `?` the list,
`Esc` closes any sheet. Never active while focus is in a text field or the embeds (the embeds take every
key while controlling). Switchable off in preferences; every shortcut has an on-screen control. Inside the
embedded viewer, keys go to the host only while the console has focus (the page's own rule), and the
macOS-caught chords are the toolbar buttons.

### 5.6 Accessibility

- Every state has a glyph and a word beside its color (SC 1.4.1): pills, chips, results, severity.
- A disabled control is `aria-disabled`, stays focusable, ignores activation, keeps its outline at full
  alpha so the box can be found (review m2), and shows its reason as visible text under or beside it (not
  a tooltip): "not offered by AMT right now", "host is already on", "identity … is missing", "the last
  server", "mounted", "no tool yet".
- Sheets are `role=dialog` with `aria-modal`, a labelled title, Escape closes, focus goes to Cancel on
  open (never to a destructive confirm), Tab is trapped inside, focus returns to the opener on close.
- Hit areas 48 × 48 CSS px (box or box plus a `::after` extension) for every control; inline chips at
  least 24 × 24 with 24 px between centers (SC 2.5.8); inline text links carry a 48 px extension and are
  measured with it.
- Focus ring 3 px `primary` with a 2 px `surface` halo, 3:1 or better everywhere it lands.
- The serial embed's output is a polite `log`; the viewer frame is `role=img` with the geometry in its
  name; tables have header cells, and on the phone each value is preceded by its column name; fingerprints
  are grouped by 4 so a screen reader reads digits in chunks.
- Reduced motion: every `data-motion` element resolves to no animation; the force hold keeps its delay
  with a countdown.
- Color is never the only carrier for destructive: shape (the only labelled pill), the warning glyph,
  the words "the OS is NOT asked".

## 6. Material 3 system

### 6.1 Color

- **Seed:** `#2f5da8` (HCT hue 265, chroma 48, tone 40, a blue), chosen so the three extended hues
  (live amber 88, ok green 155, error red 25) are far from it and from each other, and because its
  TONAL_SPOT derivation puts no M3 role in a forbidden band except tertiary, which is re-derived (next
  point). The scheme is distinct from the agent-meetings teal (hue 212): a different product.
- **Scheme:** M3 dynamic color, variant `TONAL_SPOT`, contrast level 0.0. Light and dark from the one
  seed; dark is the primary theme (the operator's preference), light a full peer; the client follows
  `prefers-color-scheme` unless overridden (`data-theme="light"|"dark"` on the root, persisted; both
  measured, section 11).
- **Tertiary re-derived.** TONAL_SPOT places tertiary at seed hue + 60 = 325, inside the pink/magenta
  band: the first token run found 15 offenders, all tertiary roles. The tertiary palette is therefore
  built at hue 195 (cyan, chroma 24, the M3 tertiary chroma) at the M3 tertiary tones (light 40/100/90/10,
  dark 80/20/30/90, fixed 90/80/10/30). Tertiary is used for the sleep and hibernate pills only.
- **The operator's color rule is a predicate, not a hue band** (house rule): pink/magenta (hue 300-360,
  chroma > 10), salmon/peach (hue 0-65, tone > 65, chroma > 10), coral (hue 15-65, tone 58-75, chroma
  > 40), burgundy (hue 340-15, tone < 45, chroma 10-60), applied by the token script to every value in
  both themes and both tiers. On the shipped `tokens.json`: 0 offenders. `swatches.html` shows the status
  roles side by side for the eye (review m1).
- **Error palette re-toned** (house rule): M3's error hue 25 at tones 40/100/35/100 (light) and
  55/5/45/100 (dark), so a dark error is a saturated red (`#f0443b`) with near-black text (`#2d0001`),
  containers are solid mid-reds with white text, never a pale pink field. Dark `error` as text is
  permitted on `surface`, `surface_container_lowest` and `surface_container_low` only (4.54:1 on low),

  held force control. The chromatic status roles (live, ok, error, primary) are pairwise at least 60
  degrees apart in HCT hue: smallest gap 62.9 (live to error), both themes.
- **Disabled:** label `on_surface` at 38 % (`overlay.disabled_fg`, WCAG-exempt), outline at full alpha.

## 7. Beyond Material

M3 has no vocabulary for a session someone holds, a power state, a pin that matches or not, a call that
was refused, a destructive act, or a fingerprint. Each extension is a named token or component in
`tokens.json`, contrast-checked to the same floor, with the reason it cannot be an existing M3 role.

### 7.1 Power pills (`states.power`)

Six states, each a glyph and a word: on (`ok.container`), sleep and hibernate (`tertiary_container`),
off (`surface_container_highest` with an `outline` ring), unknown (dashed outline; also the paused
server), unreachable (`error_container`). *Why not M3 primary / secondary:* the pill is read across a fleet
grid; it must survive selection and hover, and "on" must be the one green in the system. Off and unknown
are neutral on purpose: nothing is wrong with a host that is off.

### 7.2 Live session chips (`ext.live`, `states.session`)

A held session (KVM, SOL, IDE-R) and a running recording are amber `live.container` chips with a
pulsing dot and the holder. *Why amber, why not primary:* primary is the brand and the selected state;
a live session is a state of the host that other actions depend on (opens refused). Amber is the tally
hue consoles already use for "live". `held_other` and `paused` are error chips because they block the
next action; the agent-typing strip is the neutral paused strip, because it is a pause, not a fault.

### 7.3 Pin and identity states (`states.pin`, `states.identity`, type role `data`)

A fingerprint is data, not a secret: shown in full, grouped by 4 in `data` type with the stored 16-hex
prefix in bold `primary`, so the operator can compare with MEBx by eye. The state chips (matches,
differs, unpinned, unchecked; present · synced / entered here / unused, intake minted, missing) use `ok`,
`live`, `error` and dashed neutral. *Why not a text field or a password-style mask:* masking a fingerprint
hides the one thing the operator must compare; a text field invites editing a value that only a connection
may set.

### 7.4 Results (`states.write`)

Every write ends in a `.result` row in the action's own card: accepted (`ok.container`, ReturnValue,
readback), readback unavailable (`live.container`), refused (`error_container`, the device's reason,
"nothing sent"), failed. *Why not a snackbar:* a snackbar disappears and is read away from the control
that caused it; a refusal must sit where the next attempt would start and must still be there a minute
later.

### 7.5 The consequence line and the force control (`typography.consequence`, `shape.force-control`,
`ext.hold`)

M3 has a dialog with body text and two buttons; it does not distinguish a consequence from a
description, or a destructive confirm from a plain one, and it has no notion of a confirm whose kind
depends on what the form holds. The consequence line is an extended type role (16/24/500) on its own
container; the destructive sheet paints it on `error_container`; the force control is the only labelled
pill, held to confirm, painted `hold.fill` whole while held with a bar growing under its label. *Why:* the
operator must be able to tell, before reading a word, that this sheet is the dangerous kind, and the
sheet must become that kind when the request does.

### 7.6 Coverage disclosure (`states` on the read surfaces)

Dashed chips for `unavailable` classes, counts for `truncated`, `undated`, `undecodable`, and the two
different empty states for logs. *Why:* amt-mcp discloses its own coverage (a tool must disclose its
surface); a UI that hid it would turn "not read" back into "empty", which is what the other consoles do.

### 7.7 Embedded viewers in embed mode

The KVM and serial views are not re-implemented: amt-mcp's own token-gated pages are embedded (iframe)
from the viewer front through a console route (an opaque-origin frame, authenticated by a per-page-view key: section 2.1), in an **embed mode** that serves the view and the input controls
and nothing else (recording is a tool action from the console's chrome), and the console adds what only it knows (the holder, the
agent-typing state, the macros and text with the guard, the vaulted sign-in, the capture store). *Why:* one
implementation of the live input path (the POST `input` route with its allowlists and keep-alive), and one
power / boot / media surface per screen, so the console's confirmations and immutables govern every write
the operator can reach from the console page.

### 7.8 The honest unavailable control

A capability the comparison set offers and amt-mcp has no tool for (Platform Erase, the AMT admin-password
change, adding an event subscription) is an `aria-disabled` control with the reason as visible text, in the
place where the operator would look for it. *Why not omit it:* a MeshCommander user looks for Account
Management; finding it with "no tool: change it in MEBx" is an answer, finding nothing is a search.
